# Test case ของ Pi.py

รายการเคสที่ต้องทดสอบ ไล่ตามลำดับการทำงานจริงของ `command_flow()`

**คอลัมน์ "ยืนยัน"** — 🧪 = รันจริงกับ ESP จำลองแล้ว · 📖 = อ่านจากโค้ด ยังไม่ได้รัน

---

## A. ตอนเริ่ม session (R0 · PW)

| # | เคส | ผลที่ต้องได้ | ยืนยัน |
|---|---|---|---|
| A1 | ต่อ TCP ไม่ได้ (ESP ไม่ได้เปิด / IP ผิด) | log `❌ ต่อ TM-X ที่ ... ไม่ได้` แล้วจบ session ทันที ยังไม่ยิงคำสั่งใด | 📖 |
| A2 | `R0` ไม่ตอบเลย | ค้าง 5 วิ → `TimeoutError` → `session พังกลางทาง` | 🧪 |
| A3 | `PW` ไม่ตอบเลย | เหมือน A2 แต่เกิดหลัง `R0` ผ่านแล้ว | 🧪 |
| A4 | `R0`/`PW` ตอบ `ER,...` | **เดินหน้าวัดต่อทั้ง session** — โค้ดไม่เช็ค response ของ 2 คำสั่งนี้ | 📖 |
| A5 | `R0`/`PW` ตอบข้อความมั่วที่ไม่มี `\r` | ค้าง 5 วิ เหมือน A2 (ใช้ `send_command` ที่ `recv` ครั้งเดียว จึงรอดถ้ามีไบต์ใดๆ ส่งมา) | 📖 |

⚠ A4 คือช่องโหว่ที่รู้อยู่แล้ว — โปรแกรมวัดหมายเลขผิดจะไม่มีใครรู้จนกว่าค่าจะออกมาเพี้ยน

## B. ล้างค่าเก่า (MRS / MSR)

| # | เคส | ผลที่ต้องได้ | ยืนยัน |
|---|---|---|---|
| B1 | `MRS` สำเร็จ | log `ℹ️ ใช้คำสั่งล้างค่า MRS ได้` แล้วใช้ตัวนี้ตลอด session ไม่ลอง `MSR` อีก | 🧪 |

⚠ B3/B4 ทำให้ `GM` อาจคืนค่าของชิ้นก่อนหน้ามาโดยไม่มีอะไรเตือน

## D. อ่านค่า (GM)

| # | เคส | ผลที่ต้องได้ | ยืนยัน |
|---|---|---|---|
| D1 | คืนค่าจริงตั้งแต่ครั้งแรก | ได้ค่าใน ~20 ms → ตัดสินต่อ | 🧪 |
| D2 | คืน `-9999.99` สักพัก แล้วค่อยคืนค่าจริง | วนถามทุก 20 ms จนได้ค่า (ปกติ ~10 ครั้ง) | 🧪 |
| D3 | คืน `-9999.99` ตลอด 8 วิ | `⚠️ รอ 8 วิแล้ว GM ยังไม่คืนค่าใหม่` → `UNKNOWN` → เด้งถามผู้ใช้ | 🧪 |
| D4 | คืนค่าติดลบขนาดเล็ก เช่น `-1.00` ทุกช่อง | **`NG` ทันทีใน 0 ms** — ระบบคิดว่าได้ค่าแล้ว แต่ `clean_tools` ตัดทิ้งหมดจนเหลือ list ว่าง แล้วสั่ง MCU คัดของทิ้ง | 🧪 |
| D5 | คืน `-99999` ทุกช่อง | เหมือน D3 (ขนาด ≥ 9999 = ยังไม่ใช่ค่าจริง) | 🧪 |
| D6 | ส่งไม่ครบ 8 ชุด เช่น `GM,8,` แต่ให้มา 5 ชุด | `parse_gm` คืน `None` → วนจนหมด 8 วิ → `UNKNOWN` | 📖 |
| D7 | ประกาศจำนวนไม่ตรงของจริง เช่น `GM,5,` แต่ให้มา 8 ชุด | พาร์สได้ 5 ตัวแรก → **`GM_IDX_OFFSET_X/Y` (ช่อง 6-7) กลายเป็น `None`** → offset ไม่ถูกตรวจ | 📖 |
| D8 | ไม่ขึ้นต้นด้วย `GM` | `parse_gm` คืน `None` → วนจนหมดเวลา → `UNKNOWN` | 📖 |
| D9 | กด stop ระหว่างวน `GM` | ออกทันทีด้วย `UNKNOWN` ไม่รอครบ 8 วิ | 📖 |

⚠ **D4 อันตรายที่สุดในตาราง** — ไม่มี error ไม่มีการรอ แต่สั่ง MCU คัดของทิ้งเลย

## F. ยืนยันว่าค่าเข้า DB (รอ 15 วิ)

| # | เคส | ผลที่ต้องได้ | ยืนยัน |
|---|---|---|---|
| F1 | `measured_count` ขยับภายใน 15 วิ | `✅ ชิ้นที่ n/N บันทึกแล้ว` → วนไปชิ้นถัดไป | 🧪 |
| F2 | ไม่ขยับเลยจนครบ 15 วิ | `📣 NO_DB_ROW` → เด้งถามผู้ใช้ (ปุ่ม **รับค่าจาก Pi**) | 🧪 |
| F3 | ค่ามาถึงพอดีตอนที่ modal เปิดรอคนอยู่ | `ℹ️ ค่ามาถึงระหว่างรอคำตอบ — ไม่ต้องบันทึกซ้ำ` แล้วไปชิ้นถัดไป | 📖 |
| F4 | ผู้ใช้กด **รับค่าจาก Pi** | Pi ยิงค่าเข้า Backend เอง · `image_path` = upload_failed · ไปชิ้นถัดไป | 📖 |
| F5 | กดรับค่าแต่ POST เข้า Backend ไม่สำเร็จ | `บันทึกค่าจาก Pi ไม่สำเร็จ` → จบ session | 📖 |
| F6 | กด **หยุดการวัด** ในหน้านี้ | จบ session พร้อมเหตุผล `ค่าไม่ถึงฐานข้อมูล — ผู้ใช้เลือกหยุด` | 🧪 |
| F7 | กด **ลองใหม่** ในหน้านี้ | **หยุด session** — เพราะโค้ดเช็ค `!= "accept"` ปุ่มนี้จึงไม่ควรขึ้นในเคสนี้ | 📖 |

⚠ F3 คือด่านเดียวที่กันแถวซ้ำทั้งระบบ ห้ามถอดออก

## G. การถามผู้ใช้ (ใช้ร่วมกันทั้ง T1 และ GM)

| # | เคส | ผลที่ต้องได้ | ยืนยัน |
|---|---|---|---|
| G1 | ตอบ `retry` | วนกลับไปทำขั้นเดิมซ้ำ (T1 → ส่ง MRS+T1 ใหม่ · GM → วน GM ใหม่) | 🧪 |
| G2 | ตอบ `stop` | จบ session ทันที | 🧪 |
| G3 | ไม่ตอบจนครบ 60 วิ | `⏱ ไม่มีคำตอบใน 60 วิ — ถือว่าหยุด` | 📖 |
| G4 | Backend ตอบ HTTP ไม่ใช่ 200 ตอนส่งคำถาม | `⚠️ Backend ไม่รับคำถาม` → ถือว่าหยุด | 📖 |
| G5 | ยิงคำถามไป Backend ไม่ได้เลย (เน็ตหลุด) | `⚠️ ถามผู้ใช้ไม่ได้` → ถือว่าหยุด | 📖 |
| G6 | ครบโควตา (`rounds >= MAX_ASK_USER_ROUNDS`) | `📣 T1_GAVE_UP` / `GM_GAVE_UP` แล้วจบ **ไม่ถามอีก** | 🧪 |
| G7 | กด stop จากหน้าเว็บตอน modal ยังเปิดอยู่ | `ask_user` หลุดทันที ไม่รอครบ 60 วิ | 📖 |

**นับรอบให้ถูก** — `MAX_ASK_USER_ROUNDS = n` แปลว่า **ยิงคำสั่ง n ครั้ง · ถามผู้ใช้ n−1 ครั้ง**

| ค่าที่ตั้ง | ยิง T1 | ถามผู้ใช้ |
|---|---|---|
| 3 (ปัจจุบัน) | 3 | 2 |
| 4 | 4 | 3 |

⚠ ถ้า TM-X ตอบ `ER,T1,03` ให้คูณด้วย `T1_RETRY` อีก → ตั้ง 3 จะยิงจริง 9 ครั้ง

## ลำดับการทดสอบที่แนะนำ

1. **A1 → A2 → C1 → D1 → E1 → F1** — เส้นทางปกติให้ผ่านก่อน ถ้าเส้นนี้ยังไม่ผ่านอย่าเพิ่งไปเทสต์เคสพัง
2. **C6** — เช็ก `\r` ให้ครบทุกคำสั่ง เป็นบั๊กที่เจอบ่อยที่สุดตอนเขียนเฟิร์มแวร์ใหม่
3. **D4** — เคสที่อันตรายที่สุด ต้องแน่ใจว่า ESP ใช้ `-9999.99` ไม่ใช่ค่าเล็กๆ
4. **C3 · D3 · F2** — 3 เส้นทางที่เด้งถามผู้ใช้ ทดสอบว่า modal ขึ้นถูกแบบ
5. **G6 · I4** — ยืนยันว่าจบ session อย่างถูกต้องและ log บอกเหตุผลชัด
