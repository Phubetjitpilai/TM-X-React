## 1. ภาพรวมผลิตภัณฑ์

**TM-X5000** = คอนโทรลเลอร์ · **TM-X5065** = หัวเซนเซอร์ (ตัวส่ง + ตัวรับ + ฐาน)

เป็นเครื่องมือวัดโปรไฟล์ความเร็วสูงระบบ **เทเลเซนตริก** (telecentric) — วัดจากเงาของชิ้นงานที่บังลำแสง จึงวัดได้โดยไม่ต้องสัมผัส และค่าที่ได้ไม่เพี้ยนตามระยะที่ชิ้นงานวางในระยะชัดลึก

หนึ่งคอนโทรลเลอร์ต่อหัวได้ **2 หัว** (เรียก หัว A / หัว B) — โปรเจกต์เราใช้หัวเดียว

## 5. คำสั่งที่โปรเจกต์เราใช้ — รายละเอียดเต็ม

### 5.1 `R0` — สลับเป็นโหมดดำเนินงาน

`5-4 (PDF 82)`

```
ส่ง :  R0
รับ :  R0
```

เปลี่ยนจากโหมดตั้งค่า → โหมดดำเนินงาน **การปฏิบัติงานจะเสร็จสมบูรณ์ก็ต่อเมื่อสั่งงานในโหมดดำเนินงานแล้ว**

ผลลัพธ์: `0` สำเร็จ · `22` มีพารามิเตอร์ที่ไม่จำเป็นรวมอยู่ด้วย

**สมรรถนะเรียลไทม์**: เรียกใช้ทันที

### 5.2 `PW` — เปลี่ยนโปรแกรมการตรวจสอบ

`5-7 (PDF 85)`

```
ส่ง :  PW,d,nnn
รับ :  PW
```

| พารามิเตอร์ | ความหมาย |
|---|---|
| `d` | หมายเลขการ์ด SD — `1` = SD1, `2` = SD2 |
| `nnn` | หมายเลขโปรแกรม **0 ถึง 999** |

**สิ่งที่เกิดขึ้น** — ปิดกล่องโต้ตอบที่เปิดอยู่ทั้งหมด แล้วโหลดโปรแกรมหมายเลข `nnn` จากการ์ด SD

> ⚠ **การเปลี่ยนแปลงใดๆ ต่อข้อมูลการตั้งค่าจะถูกยกเลิก** — ถ้าอยากให้หมายเลขโปรแกรมคงอยู่หลังเปลี่ยน ต้องบันทึกด้วยคำสั่ง `SS`

**ผลลัพธ์**

| รหัส | ความหมาย |
|---|---|
| `0` | สำเร็จ |
| `03` | ไม่มีหมายเลขโปรแกรมนั้น · ไม่ได้ใส่การ์ด SD หรือเข้าถึงไม่ได้ · ออกคำสั่งในโหมดตั้งค่า · คำสั่งถูก "BLOCK" |
| `22` | จำนวนหรือช่วงของพารามิเตอร์ไม่ถูกต้อง |

**สมรรถนะเรียลไทม์**: ถ้ากำลังสั่งงานเครื่องมืออยู่ จะรอให้เสร็จก่อนแล้วค่อยทำ

> โค้ดเราส่ง `PW,1,{template:03d}` = SD1 + เลขโปรแกรม zero-pad 3 หลัก ✅ ถูกต้องตามสเปก

### 5.3 `MSR` — รีเซ็ตค่าที่วัดได้ ⚠ จุดที่คู่มือพิมพ์ไม่ตรงกันเอง

`5-9 (PDF 87)`

```
ส่ง :  MSR
รับ :  MSR
```

> ### ⚠ ข้อควรระวังสำคัญ
>
> **หัวข้อของหน้าเขียนว่า `MRS` แต่ช่องส่ง/รับ ในหน้าเดียวกันเขียนว่า `MSR`**
> และตารางรายการคำสั่งที่ `5-3 (PDF 81)` ก็เขียนว่า `MRS`
>
> ยืนยันแล้วจากการอ่าน PDF โดยตรง — **คู่มือขัดแย้งกันเอง ไม่ใช่เราอ่านผิด**
>
> โค้ดใน `Pi.py` จึงลองยิงทั้งสองตัว (`CLEAR_CANDIDATES = ["MRS", "MSR"]`) แล้วจำตัวที่ผ่าน — เป็นวิธีที่ถูกต้องแล้วในสถานการณ์นี้
>
> **หลักฐานเสริม**: ในตารางสัญญาณ EtherNet/IP ที่ `5-21 (PDF 99)` KEYENCE ใช้ชื่อ `MSR_VALID` และ `MSR_RESET` — สะกด **MSR** ทั้งคู่ จึงมีน้ำหนักว่า `MSR` น่าจะเป็นตัวที่ถูก

**ทำอะไร** — ขอให้รีเซ็ตค่าที่วัดได้ **สำหรับหมายเลขรูปแบบที่ใช้งานอยู่** (ไม่ใช่ทุกรูปแบบ)

ผลลัพธ์: `0` สำเร็จ · `03` ออกคำสั่งในโหมดตั้งค่า / คำสั่งถูก BLOCK · `22` มีพารามิเตอร์ที่ไม่จำเป็น

**สมรรถนะเรียลไทม์**: เวลาในการประมวลผลการวัดจะไม่ได้รับผลกระทบ

**ตัวที่ใกล้เคียง** — `RSA` (เลข 55) ทำแบบเดียวกันแต่กับ **ทุกหมายเลขรูปแบบ** รวมที่ไม่ได้ใช้งานอยู่ด้วย

### 5.4 `T1` — ส่งทริกเกอร์

`5-4 (PDF 82)`

```
ส่ง :  T1
รับ :  T1
```

**ผลลัพธ์**

| รหัส | ความหมาย |
|---|---|
| `0` | สำเร็จ |
| **`03`** | • ไม่สามารถยอมรับทริกเกอร์ได้ หรืออินพุตทริกเกอร์ถูกปิดใช้งาน (**เมื่อไม่มีการเปิด READY**)<br>• ออกคำสั่งในโหมดตั้งค่า<br>• คำสั่งมีปัญหา การทำงานถูก "BLOCK" |
| `22` | มีพารามิเตอร์ที่ไม่จำเป็นรวมอยู่ด้วย |

**สมรรถนะเรียลไทม์**: เวลาในการประมวลผลการวัดจะไม่ได้รับผลกระทบ

> ### 💡 อธิบาย `Er,03` ที่โค้ดเรา retry
>
> `03` แปลว่า **"รับคำสั่งแล้วแต่ทำไม่ได้ตอนนี้"** ไม่ใช่ "คำสั่งผิด" (นั่นคือ `02`)
>
> สาเหตุที่พบบ่อยที่สุดของเราคือ **READY ยังไม่กลับมา** หลัง `R0`/`PW` — เพราะ `PW` ต้องโหลดโปรแกรมจากการ์ด SD ซึ่งกินเวลา ระหว่างนั้น READY จะยังปิดอยู่ ยิง `T1` ไปก็โดนปฏิเสธ
>
> การ retry `T1` 3 ครั้งห่างกัน 0.3 วิ (`T1_RETRY` / `T1_RETRY_WAIT`) จึงเป็นวิธีที่ตรงกับพฤติกรรมจริงของเครื่อง
>
> **ทางเลือกที่สะอาดกว่าถ้าจะทำในอนาคต** — ใช้คำสั่ง `RM` (เลข 16, อ่านโหมดปัจจุบัน) เช็คว่าเข้าโหมดดำเนินงานแล้วจริงก่อนยิง `T1` แทนการเดาด้วย `sleep`

> ### ⚠ `T1` ตอบกลับตอน "รับทริกเกอร์" ไม่ใช่ตอน "วัดเสร็จ"
>
> คู่มือระบุว่าเวลาถ่ายภาพ (ช่วงทริกเกอร์) ≈ **24 ms** ที่ช่วงการวัดเต็ม
> ดังนั้นได้ `T1` ตอบกลับมาไม่ได้แปลว่าค่าพร้อมให้ดึงแล้ว — ต้องวน `GM` ถามจนกว่าจะได้ค่าใหม่ ซึ่งตรงกับที่ `get_measurement_tmx()` ทำอยู่

### 5.5 `GM` — ดึงข้อมูลค่าที่วัดได้ (คำสั่งที่ซับซ้อนที่สุดที่เราใช้)

`5-15 (PDF 93)`

```
ส่ง :  GM,o,t,nnn,…,nnn
```

**รูปแบบการตอบกลับ เปลี่ยนตามค่า `o`**

| `o` | ความหมาย | รูปแบบที่ได้รับ |
|---|---|---|
| `0` | ค่าที่วัดได้เท่านั้น | `GM,t,m,…,m` |
| `1` | ค่าที่วัดได้ + ข้อมูลผลการวัด | `GM,t,m,i,…,m,i` |
| `2` | ค่าที่วัดได้ + ผลการตัดสิน | `GM,t,m,j,…,m,j` |
| **`3`** | **ค่าที่วัดได้ + ข้อมูลผลการวัด + ผลการตัดสิน** | **`GM,t,m,i,j,…,m,i,j`** |

**พารามิเตอร์**

| ชื่อ | ความหมาย |
|---|---|
| `o` | หัวข้อเอาต์พุต (0–3 ตามตารางบน) |
| `t` | จำนวนเครื่องมือที่จะดึง — **`t ≤ 12`** · ระบุ **`0` = เครื่องมือทั้งหมด** |
| `nnn` | ID ของเครื่องมือที่จะดึง — ช่วง **200–299** และ **500–599** |
| `m` | ค่าที่วัดได้ |
| `i` | ข้อมูลผลการวัด — `0` ไม่มีการดำเนินการ · `1` ค่าปกติ · `2` การแก้ไขตำแหน่งล้มเหลว · `3` ข้อมูลไม่ถูกต้อง · `4` ข้อมูลเตรียมพร้อมรอการตัดสิน |
| `j` | ผลการตัดสิน — **`0` = OK · `1` = NG** |

**ผลลัพธ์**

| รหัส | ความหมาย |
|---|---|
| `0` | สำเร็จ |
| `03` | • **ไม่มีค่าที่วัดได้ให้ดึง (ไม่ได้อินพุตทริกเกอร์)**<br>• ออกคำสั่งในโหมดตั้งค่า<br>• คำสั่งถูก BLOCK |
| `22` | • จำนวนหรือช่วงพารามิเตอร์ไม่ถูกต้อง<br>• ระบุ ID เครื่องมือนอกช่วง<br>• ID เครื่องมือซ้ำกัน<br>• (Non-Procedural) จำนวนเครื่องมือเป้าหมายกับจำนวน ID ที่ส่งไม่ตรงกัน |

**สมรรถนะเรียลไทม์**: เวลาในการประมวลผลการวัดจะไม่ได้รับผลกระทบ

> ### 💡 ถอดรหัส `GM,3,0` ที่โค้ดเราใช้
>
> `o=3` → ขอครบทั้ง 3 อย่าง (ค่า + ข้อมูลผล + การตัดสิน)
> `t=0` → เอาเครื่องมือทั้งหมด จึงไม่ต้องระบุ `nnn` ต่อท้าย
>
> สิ่งที่ได้กลับมาคือ `GM,t,m,i,j,m,i,j,…` โดย `t` ตัวแรกคือ **จำนวนเครื่องมือ** ที่ตามมา แล้วจึงเป็นชุดละ 3 ค่าต่อเครื่องมือ 1 ตัว
>
> **ค่า `i` มีประโยชน์มากกว่าที่เราใช้อยู่** — `i=4` แปลว่า "ข้อมูลเตรียมพร้อมรอการตัดสิน" คือ TM-X ยังคำนวณไม่เสร็จ ส่วน `i=3` แปลว่า "ข้อมูลไม่ถูกต้อง" ซึ่งเป็นคนละเรื่องกัน ตอนนี้โค้ดเรากรองด้วยค่า sentinel `-9999.999` ถ้าเปลี่ยนมาดู `i` แทนจะแม่นกว่าและอธิบายสาเหตุได้ตรงกว่า

### 5.6 `S0` — สลับเป็นโหมดตั้งค่า

`5-4 (PDF 82)`

```
ส่ง :  S0
รับ :  S0
```

สลับจากโหมดดำเนินงาน → โหมดตั้งค่า **การปฏิบัติงานเสร็จสมบูรณ์ก็ต่อเมื่อสั่งงานในโหมดตั้งค่าแล้ว**

ผลลัพธ์: `0` สำเร็จ · `22` มีพารามิเตอร์ที่ไม่จำเป็น

**สมรรถนะเรียลไทม์**: ถ้ากำลังสั่งงานเครื่องมืออยู่ จะรอให้เสร็จก่อน

> ⚠ **โค้ดปัจจุบันไม่ได้ส่ง `S0` แล้ว** (เหลือแต่ในคอมเมนต์) — ตอนจบ session แค่ปิด socket เฉยๆ
>
> ผลคือ **TM-X ยังค้างอยู่ในโหมดดำเนินงาน** ซึ่งใช้งานได้ปกติ (session ถัดไปยิง `R0` ซ้ำก็ไม่มีปัญหา) แต่ถ้าจะไป present อย่าอ้างว่ามี `S0` เพราะไม่ตรงกับโค้ด

```
ER,**,nn
```

### 6.2 ตารางรหัส

| รหัส | ความหมาย | ตีความ |
|---|---|---|
| `0` | สำเร็จ | |
| `02` | **ข้อผิดพลาดคำสั่ง** — คำสั่งที่ได้รับไม่ถูกต้อง | สะกดคำสั่งผิด / ไม่มีคำสั่งนี้ ← ถ้าเจอ `ER,MRS,02` แปลว่าต้องใช้ `MSR` |

## 7. เอาต์พุตผลลัพธ์และภาพ (ส่วนที่ Data Receiver เกี่ยวข้อง)

`3-34 → 3-35 (PDF 60–61)`

### 7.1 เอาต์พุตผลลัพธ์ (ไฟล์ค่า)

**ปลายทางที่เลือกได้** — SD การ์ด · USB HDD · **เซิร์ฟเวอร์ FTP** · Non-Procedural (RS-232C / Ethernet) · ฟิลด์เน็ตเวิร์ค

| ปลายทาง | โฟลเดอร์ | ชื่อไฟล์ |
|---|---|---|
| SD / USB HDD | **กำหนดไว้ตายตัว** เช่น `SD2:\tm-x\result\SD1_001` | `[yymmdd]_[hhmmss].csv` |
| **FTP** | **ระบุเองได้** | **`[yymmdd]_[hhmmss].txt`** |

> ✅ **ตรงกับที่ `Recieve_tm-x.py` เจอ** — ไฟล์ค่าที่ TM-X ส่งมาเป็น `.txt` เพราะปลายทางเป็น FTP (ถ้าเป็น SD จะได้ `.csv` แทน)

**ข้อจำกัดการเลือกปลายทาง**

- เลือก `SD การ์ด` + `USB HDD` พร้อมกันไม่ได้
- เลือก `USB HDD` + `เซิร์ฟเวอร์ FTP` พร้อมกันไม่ได้
- ถ้ากำลังเอาต์พุต**ภาพ**ไปที่ `USB HDD` จะเลือก `FTP` เป็นปลายทางผลลัพธ์ไม่ได้ และกลับกัน

**โหมดเอาต์พุต** — `อัปเดตทุกครั้งที่มีการตัดสิน` · `คงสถานะ` (คงไว้จนกว่าจะรีเซ็ตตัวนับ) · `เอาต์พุตวันช็อต`

### 7.2 เอาต์พุตภาพ

**ปลายทาง** — `SD การ์ด` / **`FTP`** / `USB HDD` — **[โฟลเดอร์ปลายทาง] ระบุเองได้เฉพาะเมื่อเลือก FTP เท่านั้น**

**กฎการตั้งชื่อ** ตั้งได้ 3 อย่าง: กฎการแบ่งโฟลเดอร์ · กฎการตั้งชื่อแฟ้ม · รูปแบบแฟ้ม

เมื่อเลือก `ปรับแต่งเอง` ประกอบชื่อไฟล์จากส่วนประกอบเหล่านี้ได้: ค่าที่วัดได้ · ผลลัพธ์การวิเคราะห์ · ตัวแปรระบบ · วันที่/เวลา · สตริง · สตริงที่ระบุภายนอก · ข้อมูลที่ใช้ระบุภาพ

> ### ⚠ คำเตือนจากคู่มือที่ตรงกับปัญหาของเรา
>
> - **"เมื่อชื่อแฟ้มว่าง จะไม่มีการส่งออกภาพ"**
> - **"แฟ้มที่ใช้ชื่อเดียวกันจะถูกเขียนทับ"** ← ตรงกับพฤติกรรมที่เราออกแบบไว้ว่ารูปของ ALPL เดิมในวันเดียวกันจะทับกัน
> - เมื่อเปิด [บัฟเฟอร์ภาพ] จะแสดง [สตริงที่ระบุภายนอก] ได้ไม่ถูกต้อง

**ลำดับความสำคัญ** — เลือกได้ว่า `ประมวลผลการวัดก่อน` หรือ `ประมวลผลภาพก่อน`

> 💡 **น่าสนใจสำหรับเรา** — ค่านี้มีผลต่อลำดับที่ TM-X ส่งไฟล์ `.txt` กับไฟล์รูปออกมา ซึ่ง `Recieve_tm-x.py` พึ่งพาลำดับการมาถึงในการจับคู่ ถ้าวันหนึ่งจับคู่ผิด ให้มาดูค่านี้เป็นอันดับแรก

**คำสั่งที่เกี่ยวข้อง**

- `OW,n` — เปลี่ยนไฟล์/โฟลเดอร์เอาต์พุต: `0` ไฟล์ผลลัพธ์ · `1` โฟลเดอร์ภาพ · `2` โฟลเดอร์ภาพมอนิเตอร์อย่างง่าย (สร้างใหม่โดยใช้วันที่/เวลาล่าสุด)
- `OE,n` — `0` ปิดเอาต์พุต (**และล้างข้อมูลในบัฟเฟอร์ทิ้ง**) · `1` เปิด
  - ⚠ ผลลัพธ์ที่เกิดขึ้นระหว่างที่เอาต์พุตปิดอยู่ **จะถูกยกเลิกไปเลย ไม่ได้ค้างรอ**

| `OUTPUT_IMG_BUSY` | เอาต์พุตขณะกำลังส่งภาพออก |
| `OUTPUT_IMG_STATUS` | เอาต์พุตเมื่อมีภาพนิ่งค้างรออยู่ในบัฟเฟอร์ |
| `Tool Judge Value0…63` | ค่าตัดสินรายเครื่องมือ |

> 💡 **`MSR_VALID` คือทางเลือกที่ดีกว่าการ poll `GM`** — ถ้าอนาคตต่อฟิลด์เน็ตเวิร์คหรือเทอร์มินอลได้ จะรู้ทันทีว่าค่าพร้อมหรือยัง แทนที่จะวนถาม `GM` ทุก 0.x วิแล้วเทียบกับค่าเดิม

### 8.2 สัญญาณจากภายนอก → TM-X (อินพุต)

`TRG` · `RESET` · `EXT` · `TEST` · `TIMING` · `ZERO_ON` · `ZERO_OFF` · **`MSR_RESET`** · `RESET_ALL` · `Cmd request` · `Result ack` · `ร้องขอการรีเซ็ตข้อผิดพลาด`

> `MSR_RESET` (อินพุตแบบบิต) ทำงานเดียวกับคำสั่ง `MSR` — คู่มือระบุว่าคำสั่งที่มีเครื่องหมาย `*1` ในตารางหน้า `5-3` **เรียกใช้ได้ทั้งจากคำสั่งข้อความและจากอุปกรณ์แบบบิต**

### 8.3 `TE` — ปิดการรับทริกเกอร์

`5-10 (PDF 88)` · `TE,0` → **เทอร์มินอล `READY` จะถูกตั้งให้ปิดอยู่** จึงไม่มีทริกเกอร์ใดถูกยอมรับ · `TE,1` → กลับมารับปกติ

- สถานะปิดใช้งานของทริกเกอร์ **ไม่ได้ถูกบันทึกไว้ในการตั้งค่า** — ปิดแล้วเปิดเครื่องใหม่จะกลับมารับทริกเกอร์ได้เอง
- ฟังก์ชัน `TE` เป็นแบบเดียวกับเทอร์มินอล `EXT` โดยสถานะปิดคือ **OR** ของทั้งสองตัว

## 9. หมายเหตุทั่วไปเรื่องการส่งคำสั่ง

`5-2 (PDF 80)`

- **ยอมรับการอินพุตคำสั่งระหว่างการดำเนินการได้** แต่ถ้าเรียกคำสั่งในสายการผลิตความเร็วสูง **การเรียกใช้คำสั่งอาจระงับการรับทริกเกอร์ได้**
- **เวลาในการเรียกใช้คำสั่งไม่คงที่** — ขึ้นกับโหลดของคอนโทรลเลอร์และประเภทการดำเนินการที่ทำอยู่ ถ้าโปรแกรมต้องรอให้คำสั่งเสร็จก่อนเริ่มตรวจสอบถัดไป **ต้องเผื่อการผันผวนของเวลารอไว้**

> 💡 ข้อนี้สนับสนุนดีไซน์ปัจจุบันของเรา — `MEASURE_TIMEOUT` 15 วิ และ `GM_MAX_WAIT` 8 วิ ตั้งเผื่อไว้เยอะกว่าเวลาถ่ายภาพจริง (~24 ms) มาก เพราะเวลาที่ไม่แน่นอนอยู่ที่คอนโทรลเลอร์กับเครือข่าย ไม่ใช่ที่การถ่ายภาพ

> ### 🐛 พบระหว่างตรวจสอบ — `clean_tools()` ทำไม่ตรงกับ docstring ของตัวเอง
>
> `Pi.py:403-408`
>
> ```python
> def clean_tools(tools):
>     """คัดกรองเอาเฉพาะข้อมูลที่สถานะ (index 1) ไม่เป็น 0 และ 3"""
>     ...
>     return [item for item in tools if str(item[0]) != "-9999.999"]
> ```
>
> **สามอย่างที่ไม่ตรงกัน**
>
> 1. docstring บอกว่ากรองที่ **index 1** (คือฟิลด์ `i` ของ `GM`) แต่โค้ดกรองที่ **index 0** (คือค่าที่วัดได้ `m`)
> 2. docstring บอกว่ากรองสถานะ `0` กับ `3` แต่โค้ดเทียบกับ sentinel `-9999.999`
> 3. `str(item[0])` แปลง float เป็นสตริงแล้วเทียบตรงตัว — ถ้า TM-X ส่ง `-9999.9990` หรือ `-9999.999` มาในรูปแบบที่ต่างออกไปเล็กน้อย จะเทียบไม่ติด **และ `has_real_value()` ที่อยู่ในไฟล์เดียวกันใช้ `abs(m) < NO_VALUE_ABS` ซึ่งเป็นวิธีที่ทนกว่า**
>
> ตามคู่มือ ฟิลด์ `i` คือช่องทางที่ถูกต้องสำหรับเรื่องนี้ — `i=3` ข้อมูลไม่ถูกต้อง · `i=4` ยังรอการตัดสิน
> ถ้าจะแก้ ให้กรองที่ `item[1]` ตามที่ docstring ตั้งใจไว้ แทนการเทียบสตริง
